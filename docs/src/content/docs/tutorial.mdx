cd web-push && pnpm install && pnpm run build
cd examples/app && pnpm install

Three things in it are deliberate:

- **The service worker is registered on load, and `subscribe` runs on a click.** Browsers only show the permission prompt in response to a user gesture, and registering early means the prompt doesn't wait on it.
- **A visitor who is already subscribed is subscribed again on every visit.** That doesn't prompt. It replaces a subscription bound to an old VAPID key, and the upload is an upsert, so the server always holds the current subscription even if an earlier upload failed. A visitor who turned notifications off stays off, though their permission is still granted.
- **Turning notifications off removes the server's record too.** [`unsubscribe`](/reference/client/#unsubscribe) resolves to the endpoint for exactly this, even when the browser fails to unsubscribe.

The rest of the server is one fetch handler, `(request) => response`, so every runtime shares all of it:

<Code code={appTs} lang="ts" title="src/app.ts" />

Its four routes:

| Route                        | What it does                                                                                 |
| ---------------------------- | -------------------------------------------------------------------------------------------- |
| `GET /api/vapid-public-key`  | Hands the page the public key to subscribe with                                              |
| `POST /api/push/subscribe`   | Saves a subscription, the default route of `sendSubscriptionToServer`                        |
| `DELETE /api/push/subscribe` | Forgets one, the default route of `removeSubscriptionFromServer`                             |
| `POST /api/push/broadcast`   | Pushes a payload to every subscriber, deletes the ones that are gone, and reports the counts |

Saving rejects any endpoint that isn't a known push service. The server will later POST to whatever URL a subscription names, and a subscription comes from a browser you don't control; [Secure your endpoints](/guides/secure-endpoints/) explains why that matters.

## 6. Send a notification

Broadcast to everyone subscribed, with the admin token from step 1. On Workers, use port 8787:

```bash
curl -X POST http://localhost:3000/api/push/broadcast \
  -H "Authorization: Bearer <your ADMIN_TOKEN>" \
  -d '{ "title": "Hello", "body": "Your first push", "url": "/" }'
```

The response counts what happened: `delivered` were accepted by their push service, `removed` were gone (the browser unsubscribed or the subscription expired) and have been deleted, and `failed` didn't go through this time.

## 7. Before production

The example keeps each part small. A real deployment usually wants:

- **A durable store.** A database table keyed by endpoint, instead of memory or a KV listing that reads every key.
- **Subscriptions tied to users,** so you can push to one person's devices rather than everyone. See [Authenticated uploads](/guides/authenticated-uploads/).
- **Retries for `failed`,** sorted by error type. See [Handle errors and retries](/guides/handle-errors/).
- **Sending in pages** once the subscriber list is large. See [Send to many](/guides/send-to-many/).
- **A plan for rotating keys.** See [Rotate VAPID keys](/guides/rotate-vapid-keys/).
- **Real authentication on the broadcast route,** rather than one shared token.
